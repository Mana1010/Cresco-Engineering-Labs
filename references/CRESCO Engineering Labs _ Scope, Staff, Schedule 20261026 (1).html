01 · Scope boundary

One Engineering Labs experience across multiple tools.

The portal provides the common management, access and integration experience, while each engineering tool or service continues to own its specialist calculation, classification, parsing or drafting capability.

Portal responsibility

Engineering Labs Portal

  • Program / tool registration and catalogue
  • Staff authentication, authorization and access controls
  • Launch, embedded or API-based tool access patterns
  • Integration configuration, credentials and version routing
  • Input handoff and result retrieval where interfaces support it
  • Result views, report retrieval, history and audit references
  • Integration health, error handling, deployment and handover
Integration
contract
Tool / service responsibility

Engineering tools & services

  • Engineering formulas, standards and calculation logic
  • Reference datasets and proprietary classification rules
  • Parsing / drafting / solver engines
  • Numerical correctness and engineering validation
  • Supported input/output contracts and tool versions
  • Tool-specific subscriptions, usage constraints and licensing
  • Representative benchmarks and expected engineering outputs
Scope alignment principle

Where a capability is already provided by an engineering tool or external service, Portal scope is centered on registration, authorized access, interface contracts, data exchange, results, reporting and operational control. Tool engineering logic remains with the relevant tool or service owner unless separately agreed.

Technical Integration Implementation Architecture & Flow

All integration interfaces are built to align with the PostgreSQL `cresco_eng_` prefixed normalized data model, using UUID primary key mapping to avoid cross-system ID collisions, with dedicated indexing strategies to optimize cross-system join performance:

  1. Unified ID Mapping Layer: A central `cresco_eng_system_id_mappings` table with UUID primary key, composite index on `source_system_type` and `external_system_id` is deployed to maintain a consistent mapping between portal internal entity UUIDs and external system record IDs, eliminating duplicate data synchronization conflicts.
  2. Event-Driven Synchronization Pipeline: A low-latency message broker ingests change events from all connected source systems, triggers incremental sync jobs that validate data against the normalized `cresco_eng_` table schemas: for example, test equipment booking records are mapped to the `cresco_eng_lab_booking` table, simulation output metadata is written to the `cresco_eng_simulation_run` table, with GIN indexes added to JSONB fields storing raw external system payloads to support fast filter queries.
  3. Bi-directional Integration Logic: For write-back capable systems, the portal exposes standardized REST and gRPC endpoints: when an engineer submits a test request via the portal, the system automatically pushes the request record to the PLM system to update associated work item status, and pulls updated test result data back into the `cresco_eng_test_result` table with a dedicated B-tree index on `associated_design_uuid` to speed up design-to-test traceability queries

  1. Central API Gateway/Identity Proxy System: Serves as the primary enforcement point for all incoming requests to the portal, hosting X-API-Key header validation and rate limiting logic
  2. M365 Entra ID Tenant (Staff Directory): Hosts staff identity records, SSO authentication endpoints, and group/role authorization mappings

---

Technical Integration Implementation Flow
  1. X-API-Key Validation Integration: All inbound requests to the CRESCO Engineering Labs Portal first route to the integrated API gateway layer, which extracts the X-API-Key header, validates its existence, cryptographic signature, and active status against records stored in the internal caller access control directory. Invalid or missing key requests are immediately rejected with a 401 Unauthorized response before reaching any portal business logic.
  2. Rate Limiting Integration: The API gateway pulls pre-configured rate limit thresholds (per request source IP, X-API-Key tier, and authenticated user identity) from the access control directory, tracks request counters in a distributed shared cache, and enforces throttling for requests exceeding allowed quotas, returning a 429 Too Many Requests response with appropriate Retry-After headers.
  3. M365 Entra ID Staff SSO Integration: The portal frontend and backend are registered as an enterprise application in the target M365 Entra ID tenant, using OAuth 2.0 OpenID Connect authentication flow. Unauthenticated staff users are automatically redirected to the Entra ID SSO endpoint for credential validation, after which Entra ID returns an ID token and access token to the portal, which the portal validates against Entra ID public signing keys to confirm identity legitimacy.
  4. Caller Authorization Integration: For human SSO users, the portal pulls Entra ID group membership and assigned role claims from the validated identity token, cross-references these claims with internal portal resource access rules to grant only permitted lab portal functionality.
